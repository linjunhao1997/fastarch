# Feature Specification: RBAC 基础管理（用户 / 角色 / 权限）

**Feature Branch**: `002-rbac-management`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "规格化用户管理，角色管理，权限管理"。经确认，范围为**目标态**：涵盖已实现的增、查、列、改能力，并纳入缺失的**删除能力**与**账号-角色绑定管理**，后续按规格补齐实现。

---

## 背景与现状

系统采用基于角色的访问控制（RBAC）：权限是最小授权单元，角色是权限的集合，账号通过被赋予角色间接获得权限。当前账号、角色、权限三个管理域已具备基础的创建、查询、列表、修改能力，角色与权限之间已可建立/解除关联；但三个域均无删除能力，且账号与角色之间的绑定关系无法通过管理入口维护（登录时系统读取到的账号角色缺乏可管理来源）。本特性定义这三个管理域的完整目标能力。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 账号管理 (Priority: P1)

管理员在"账号管理"页面查看账号列表（支持分页），创建账号（姓名、邮箱、账号类型），以及修改既有账号的信息。

**Why this priority**: 账号是 RBAC 体系的主体，一切授权围绕账号展开；账号不可管理则整个体系无从谈起。

**Independent Test**: 通过创建表单新增一个账号，在列表中看到它，修改其信息后再次查看确认更新，即为通过。

**Acceptance Scenarios**:

1. **Given** 系统中存在若干账号，**When** 管理员打开账号列表，**Then** 分页展示账号的名称、邮箱、类型等信息，数据全部来自真实存储
2. **Given** 管理员填写完整的账号信息提交创建，**When** 邮箱未被占用，**Then** 创建成功并出现在列表中
3. **Given** 创建时邮箱已被占用，**When** 管理员提交，**Then** 系统拒绝并提示邮箱重复，不产生数据
4. **Given** 存在一个账号，**When** 管理员修改其邮箱并保存，**Then** 列表与详情展示更新后的信息
5. **Given** 存在多个账号，**When** 管理员在账号列表输入关键字搜索或按账号类型/绑定状态筛选，**Then** 列表仅展示匹配的结果，分页计数随之更新

---

### User Story 2 - 角色管理与角色-权限配置 (Priority: P2)

管理员在"角色管理"页面查看角色列表，创建角色（名称、编码），编辑角色信息，并在编辑时为角色添加或移除权限。

**Why this priority**: 角色是权限的载体，是"账号—权限"之间的桥梁；没有角色管理，权限定义只是孤立的清单。

**Independent Test**: 创建一个角色，为其添加两个权限编码，再移除其中一个，查看角色详情确认权限集合符合操作结果，即为通过。

**Acceptance Scenarios**:

1. **Given** 管理员填写角色名称与编码提交创建，**When** 编码未被占用，**Then** 创建成功并出现在角色列表
2. **Given** 创建时角色编码已存在，**When** 提交，**Then** 系统拒绝并提示编码重复
3. **Given** 存在一个角色，**When** 管理员编辑该角色并添加若干权限编码，**Then** 保存后角色关联的权限集合包含新增项
4. **Given** 角色已关联某权限，**When** 管理员在编辑中移除该权限编码并保存，**Then** 该权限不再属于此角色，且不影响其他角色对该权限的关联
5. **Given** 一次编辑中同时添加和移除不同权限，**When** 提交，**Then** 两类变更同时生效

---

### User Story 3 - 权限定义管理 (Priority: P3)

管理员在"权限管理"页面查看权限列表，创建权限（名称、编码），修改权限信息。

**Why this priority**: 权限定义是授权的最小单元，但通常由系统或管理员低频维护；优先级低于账号与角色这两个高频管理对象。

**Independent Test**: 创建一条权限，修改其名称，列表确认变更，即为通过。

**Acceptance Scenarios**:

1. **Given** 管理员填写权限名称与编码提交创建，**When** 编码未被占用，**Then** 创建成功并出现在权限列表
2. **Given** 创建时权限编码已存在，**When** 提交，**Then** 系统拒绝并提示编码重复
3. **Given** 存在一条权限，**When** 管理员修改其名称并保存，**Then** 列表展示更新后的名称
4. **Given** 某权限已被角色引用，**When** 管理员修改该权限的编码，**Then** 系统明确拒绝编码变更（引用关系以编码为纽带，编码不可变）

---

### User Story 4 - 账号-角色绑定 (Priority: P4)

管理员在独立的"账号-角色绑定管理"页面选择账号后，为其绑定（授予）一个或多个角色，或解除账号上的角色绑定；绑定结果决定账号实际拥有的权限，变更立即生效。

**Why this priority**: 绑定是 RBAC 闭环中"账号获得权限"的关键一环，但依赖账号与角色两个对象先可管理，故排在其后。

**Independent Test**: 为账号绑定角色 A，登录该账号后确认其具备角色 A 所含权限的特征；解除绑定后该特征消失，即为通过。

**Acceptance Scenarios**:

1. **Given** 账号 U 与角色 R 存在且未绑定，**When** 管理员将 R 绑定到 U，**Then** 绑定关系持久化，U 登录后的可执行权限包含 R 所含权限
2. **Given** U 已绑定 R，**When** 管理员解除绑定，**Then** U 登录后的可执行权限不再包含 R 所含权限
3. **Given** 管理员尝试为账号绑定不存在的角色编码，**When** 提交，**Then** 系统拒绝并提示角色不存在
4. **Given** 同一账号同一角色重复绑定，**When** 提交，**Then** 系统保持幂等（不产生重复绑定数据，结果视为成功或给出已绑定提示）

---

### User Story 5 - 删除能力（账号 / 角色 / 权限） (Priority: P5)

管理员可删除账号、角色、权限，删除前系统给出二次确认，并针对"被引用对象"实施引用约束。

**Why this priority**: 完善管理闭环，但被删除对象的缺失通常可以通过不使用（而非删除）来规避；引用约束的正确性要求高，放在最后独立交付。

**Independent Test**: 对未引用对象执行删除成功；对被引用对象执行删除被拒绝并收到明确提示，即为通过。

**Acceptance Scenarios**:

1. **Given** 一个未被任何角色引用的权限，**When** 管理员删除并确认，**Then** 该权限从列表消失且不可再被查询
2. **Given** 一个已被角色关联的权限，**When** 管理员尝试删除，**Then** 系统拒绝并提示需先解除引用
3. **Given** 一个未被账号绑定的角色，**When** 管理员删除并确认，**Then** 角色消失，其与权限的关联一并清除
4. **Given** 一个已绑定账号的角色，**When** 管理员尝试删除，**Then** 系统拒绝并提示需先解除绑定
5. **Given** 删除确认框弹出，**When** 管理员取消，**Then** 对象保持不变
6. **Given** 两个管理员同时操作同一对象，**When** B 在 A 删除成功后再次删除同一对象，**Then** B 收到"对象不存在"的明确提示
7. **Given** 一个已绑定角色的账号，**When** 管理员尝试删除，**Then** 系统拒绝并提示需先解除该账号的所有角色绑定

---

### Edge Cases

- 当列表数据超过一页时，翻页、排序操作结果稳定且不重复、不遗漏
- 当删除或修改的对象已被其他管理员先行变更/删除时，操作结果需明确提示，不得静默成功
- 当创建/编辑提交的字段超出长度限制或格式不合法（如邮箱格式）时，提交前给出校验提示
- 当账号绑定关系变更后，该账号已登录会话的权限必须立即生效（权限校验实时读取绑定关系，可加短 TTL 缓存），不得出现已撤销授权仍可操作的中间态
- 当后端不可用或请求失败时，页面展示明确失败提示，不得静默失败或以模拟数据冒充真实数据

## Requirements *(mandatory)*

### Functional Requirements

**账号管理**

- **FR-1**: 系统 MUST 支持账号的创建、查询、列表（分页），账号信息至少包含：唯一标识、姓名、邮箱、账号类型；列表 MUST 支持按名称/编码关键字模糊搜索，并支持按账号类型与角色绑定状态筛选
- **FR-2**: 系统 MUST 保证账号邮箱唯一，重复时拒绝创建/修改并给出明确提示
- **FR-3**: 系统 MUST 支持删除未被绑定角色引用的账号；删除已绑定角色的账号时 MUST 明确拒绝，提示需先解除该账号的所有角色绑定
- **FR-4**: 账号的登录凭证（如密码）不属于本特性管理范围，MUST 沿用现有认证体系，不在账号管理界面明文暴露

**角色管理**

- **FR-5**: 系统 MUST 支持角色的创建、查询、列表（分页）、修改，角色信息至少包含：唯一标识、名称、编码；列表 MUST 支持按名称/编码关键字模糊搜索
- **FR-6**: 系统 MUST 保证角色编码唯一；角色编码一经创建不可变更
- **FR-7**: 系统 MUST 支持在角色编辑中批量添加与批量移除权限关联，两类变更可在同一次编辑中同时生效
- **FR-8**: 系统 MUST 支持删除未绑定任何账号的角色，删除时 MUST 一并清除该角色与权限的关联

**权限管理**

- **FR-9**: 系统 MUST 支持权限的创建、查询、列表（分页）、修改，权限信息至少包含：唯一标识、名称、编码；列表 MUST 支持按名称/编码关键字模糊搜索
- **FR-10**: 系统 MUST 保证权限编码唯一；权限编码一经创建不可变更
- **FR-11**: 系统 MUST 支持删除未被任何角色引用的权限

**账号-角色绑定**

- **FR-12**: 系统 MUST 支持为账号绑定与解绑一个或多个角色，绑定关系 MUST 持久化并可查询
- **FR-13**: 系统 MUST 校验绑定操作中引用的角色真实存在，不存在的 MUST 拒绝并提示
- **FR-14**: 系统 MUST 保证同一账号-角色绑定关系唯一（重复绑定幂等处理）
- **FR-15**: 账号实际拥有的权限 MUST 且仅能由其绑定的角色所关联的权限决定（单一数据源，不允许存在绕过角色的直接授权路径）

**通用约束**

- **FR-16**: 所有管理操作 MUST 做身份与权限控制——仅具备相应管理权限的账号可执行
- **FR-17**: 所有删除操作 MUST 有明确的二次确认
- **FR-18**: 所有并发修改 MUST 可被检测（后保存方不得无痕迹覆盖先保存方的修改），冲突时 MUST 给出明确提示
- **FR-19**: 所有操作失败 MUST 返回用户可理解的错误信息，不得静默失败

*范围边界：本特性覆盖账号、角色、权限三个管理域的目标态能力。应用（Application）管理、权限订阅（Subscription）、认证策略、认证流程执行均不属于本特性，各自独立立项。*

### Key Entities *(include if data involved)*

- **账号（Account）**: 系统的使用者主体。关键属性：唯一标识、姓名、邮箱（唯一）、账号类型（用户/系统，仅为身份标记，两类账号的管理规则一致）。通过角色绑定间接获得权限。
- **角色（Role）**: 权限的命名集合。关键属性：唯一标识、名称、编码（唯一且不可变）。与权限存在多对多关联，与账号存在多对多绑定。
- **权限（Permission）**: 最小授权单元。关键属性：唯一标识、名称、编码（唯一且不可变）。被角色引用。
- **账号-角色绑定（Account-Role Binding）**: 账号与角色的多对多关联关系，是账号获得权限的唯一途径。
- **角色-权限关联（Role-Permission Link）**: 角色与权限的多对多关联关系。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员能在 2 分钟内完成"创建账号 → 创建角色 → 为角色配置权限 → 将角色绑定到账号"的完整授权流程
- **SC-002**: 任一管理列表页首屏在 2 秒内完成加载并展示真实数据（预置 1000 条以内数据时）
- **SC-003**: 全部页面展示的数据 100% 来源于系统真实存储，无任何本地模拟数据
- **SC-004**: 90% 的管理员在无帮助文档情况下，首次即可正确完成账号、角色、权限各自的完整管理流程（含删除）
- **SC-005**: 所有引用约束（删除被引用对象、绑定不存在的角色、重复编码/邮箱）100% 被系统拦截并给出明确提示
- **SC-006**: 账号登录后实际拥有的权限与其"绑定角色的权限并集"完全一致，抽检验证一致率 100%

## Clarifications

### Session 2026-09-05

- Q: 删除一个已绑定角色的账号时，系统应该如何处理？ → A: 明确拒绝删除，提示需先解除该账号的所有角色绑定（与角色/权限的引用约束策略一致，不做隐式解绑）
- Q: 管理员为账号绑定或解绑角色后，权限变更应该什么时候对该账号已登录的会话生效？ → A: 立即生效：权限校验实时读取绑定关系（可加短 TTL 缓存），变更后无需重新登录
- Q: 账号的角色绑定管理应该放在界面的什么位置操作？ → A: 独立的"账号-角色绑定管理"页面，选择账号后统一管理其角色绑定
- Q: 账号、角色、权限这三个管理列表是否需要关键字搜索/筛选能力，还是仅分页浏览？ → A: 三个列表均支持按名称/编码关键字模糊搜索；账号列表额外支持按账号类型与角色绑定状态筛选
- Q: 系统类型（system）的账号在管理上是否需要区别于普通用户账号的特殊规则？ → A: 无特殊规则：账号类型仅为身份标记，系统账号的管理操作（绑定、编辑、删除）与用户账号完全一致

## Assumptions

- 本特性为**目标态规格**：已实现的增、查、列、改能力以现状为准纳入规格，删除能力与账号-角色绑定按规格补齐实现
- 权限判定采用 RBAC 模型：账号 → 角色 → 权限，不存在直接的账号-权限授权（如需直授另行立项）
- 引用约束采用"拒绝删除"策略（先解除引用再删除），账号、角色、权限本身均不做级联删除；仅角色删除时级联清除其权限关联
- 编码类字段（角色编码、权限编码）作为跨系统引用的稳定标识，一经创建不可变更；名称等展示字段可修改
- 操作者身份与权限沿用系统现有的登录与授权体系，不新建独立的权限模型
- 数据规模预期为管理配置类低频数据（各域千条以内），性能目标按此量级设定

## Dependencies

- 依赖系统现有的账号登录与权限校验能力（管理操作需已登录且具备管理权限）
- 依赖现有账号、角色、权限三个管理域的既有数据与能力（本特性在其上补齐删除与绑定）
- 账号绑定关系的权限变更必须立即对已登录会话生效（权限校验实时读取绑定关系；缓存 TTL 等实现策略在规划阶段确定）
