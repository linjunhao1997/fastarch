# Feature Specification: 应用管理

**Feature Branch**: `003-application-management`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "规格化应用管理"。沿用上一特性确认的目标态模式：已实现的增、查、列、改能力以现状为准纳入规格，并纳入缺失的**删除能力**，后续按规格补齐实现。

---

## 背景与现状

系统内的"应用"是权限资源的归属与划分单位：角色、权限等授权数据围绕应用组织，权限订阅在应用之间流转。当前应用管理已具备创建、查询、列表（分页）、修改（含启用/停用状态）能力，但缺少删除能力。本特性定义应用管理的完整目标能力。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看应用列表 (Priority: P1)

管理员打开"应用管理"页面，分页查看所有已注册的应用（名称、应用编码、描述、启用状态），数据全部来自真实存储。

**Why this priority**: 列表是应用管理的基础视图，没有真实数据展示，其余管理操作无从验证。

**Independent Test**: 预置若干应用数据后打开列表页，分页展示内容与存储一致，即为通过。

**Acceptance Scenarios**:

1. **Given** 系统中存在若干应用，**When** 管理员打开应用列表，**Then** 分页展示应用的名称、编码、描述、启用状态
2. **Given** 应用数量超过一页，**When** 管理员翻页，**Then** 各页数据稳定、不重复、不遗漏
3. **Given** 系统中没有任何应用，**When** 管理员打开列表，**Then** 展示空列表状态而非报错

---

### User Story 2 - 创建应用 (Priority: P2)

管理员通过创建表单填写应用名称、描述并保存，系统生成应用编码，新应用出现在列表中。

**Why this priority**: 创建让应用数据从无到有，是应用参与授权体系的前提。

**Independent Test**: 通过创建表单提交一个应用，重新打开列表能看到它且编码已生成，即为通过。

**Acceptance Scenarios**:

1. **Given** 管理员填写名称与描述提交创建，**When** 名称合法，**Then** 创建成功，应用出现在列表中且拥有系统生成的唯一应用编码
2. **Given** 创建表单名称为空，**When** 提交，**Then** 系统拒绝并提示名称必填，不产生数据
3. **Given** 已存在同名应用，**When** 管理员以相同名称再次创建，**Then** 系统拒绝并提示名称重复

---

### User Story 3 - 编辑应用 (Priority: P3)

管理员修改应用的名称、描述或启用状态（启用/停用）并保存，变更在列表与后续查询中可见。

**Why this priority**: 应用信息会随环境变化，启用/停用提供不删除即生效的可用性开关。

**Independent Test**: 修改一个应用的描述并将其停用，列表确认变更即为通过。

**Acceptance Scenarios**:

1. **Given** 存在一个应用，**When** 管理员修改其描述并保存，**Then** 列表展示更新后的描述
2. **Given** 存在一个启用中的应用，**When** 管理员将其停用并保存，**Then** 列表中该应用状态变为停用
3. **Given** 编辑时名称被清空，**When** 提交，**Then** 系统拒绝保存且原数据保持不变
4. **Given** 管理员尝试修改应用编码，**Then** 系统 MUST 不提供该修改入口（编码不可变更）

---

### User Story 4 - 删除应用 (Priority: P4)

管理员删除未被任何授权数据引用的应用，删除前系统给出二次确认；被引用的应用禁止删除。

**Why this priority**: 完善管理闭环，但应用通常长期存在，删除是低频操作，且引用约束的正确性要求高。

**Independent Test**: 删除一个未被引用的应用成功；尝试删除一个被引用的应用被拒绝并收到明确提示，即为通过。

**Acceptance Scenarios**:

1. **Given** 一个未被任何授权数据（角色、权限、订阅等）引用的应用，**When** 管理员删除并确认，**Then** 该应用从列表消失且不可再查询
2. **Given** 一个被授权数据引用的应用，**When** 管理员尝试删除，**Then** 系统拒绝并提示需先解除引用
3. **Given** 删除确认框弹出，**When** 管理员取消，**Then** 应用保持不变
4. **Given** 两个管理员同时操作同一应用，**When** B 在 A 删除成功后再次删除同一应用，**Then** B 收到"应用不存在"的明确提示

---

### Edge Cases

- 当删除或修改的应用已被其他管理员先行变更/删除时，操作结果明确提示，不得静默成功
- 当创建/编辑提交的字段超出长度限制时，提交前给出校验提示
- 当应用被停用后，其在授权体系中的既有引用（角色、权限、订阅）保持不变；停用是否影响订阅流程由后续特性定义，本特性仅保证状态本身可管理
- 当后端不可用或请求失败时，页面展示明确失败提示，不得静默失败或以模拟数据冒充真实数据

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1**: 系统 MUST 支持应用的创建、查询、列表（分页）、修改，应用信息至少包含：唯一标识、名称、应用编码、描述、启用状态
- **FR-2**: 系统 MUST 保证应用名称唯一，重复时拒绝创建并给出明确提示
- **FR-3**: 系统 MUST 在创建成功时生成全局唯一的应用编码；应用编码一经创建不可变更
- **FR-4**: 系统 MUST 支持启用/停用应用，状态变更即时生效于后续查询
- **FR-5**: 系统 MUST 支持删除未被任何授权数据引用的应用
- **FR-6**: 系统 MUST 拒绝删除被授权数据引用的应用，并提示需先解除引用
- **FR-7**: 所有删除操作 MUST 有明确的二次确认
- **FR-8**: 所有并发修改 MUST 可被检测，冲突时 MUST 给出明确提示，不得无痕迹覆盖
- **FR-9**: 所有管理操作 MUST 做身份与权限控制——仅具备相应管理权限的账号可执行
- **FR-10**: 所有操作失败 MUST 返回用户可理解的错误信息，不得静默失败

*范围边界：本特性仅覆盖应用自身的生命周期管理（CRUD + 启停 + 删除）。应用与角色/权限的授权关系、应用间的权限订阅、认证策略均不属于本特性，各自独立立项。*

### Key Entities *(include if data involved)*

- **应用（Application）**: 权限资源的归属单位。关键属性：唯一标识、名称（唯一）、应用编码（系统生成、全局唯一、不可变）、描述、启用状态。被授权数据（角色、权限、订阅）以编码引用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员能在 1 分钟内完成一个应用的创建并在列表中看到它
- **SC-002**: 应用列表页首屏在 2 秒内完成加载并展示真实数据（预置 1000 条以内应用时）
- **SC-003**: 全部页面展示的数据 100% 来源于系统真实存储，无任何本地模拟数据
- **SC-004**: 90% 的管理员在无帮助文档情况下，首次即可正确完成应用的创建—编辑—停用—删除完整流程
- **SC-005**: 所有引用约束与唯一性约束（删除被引用应用、重名应用）100% 被系统拦截并给出明确提示
- **SC-006**: 所有已创建应用拥有全局唯一编码，抽检验证重复率 0%

## Assumptions

- 本特性为**目标态规格**：已实现的增、查、列、改（含启停）能力以现状为准纳入规格，删除能力按规格补齐实现
- 沿用上一特性（RBAC 基础管理）确认的模式：引用约束采用"拒绝删除"策略，不做级联删除
- 应用编码由系统生成而非用户填写，作为跨系统引用的稳定标识，一经创建不可变更；名称可修改但需唯一
- 应用被停用不影响既有授权数据的存在性，停用的业务影响（如订阅流转受限）由订阅相关特性定义
- 操作者身份与权限沿用系统现有的登录与授权体系，不新建独立的权限模型
- 数据规模预期为管理配置类低频数据（千条以内），性能目标按此量级设定

## Dependencies

- 依赖系统现有的账号登录与权限校验能力（管理操作需已登录且具备管理权限）
- 依赖现有应用管理域的既有数据与能力（本特性在其上补齐删除）
- 授权数据（角色、权限、订阅）对应用的"引用"判定以应用编码为纽带，与授权域的现有数据模型保持一致
