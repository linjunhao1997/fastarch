# Feature Specification: AK/SK 签名鉴权凭证管理

**Feature Branch**: `009-ak-sk-auth`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "现在我有新的需求，要求接口可以通过 ak 或 sk 进行签名鉴权来调用，ak 或 sk 需要通过绑定一个用户来创建，给我添加新的模型->接口->前端页面，这个应该属于 iam 的用户管理还是认证管理"

## 领域归属裁决（回答用户问题）

**该功能属于 IAM 的「认证管理」（Authentication Management）域，不属于「用户管理」域。**

裁决依据：

- AK/SK（Access Key / Secret Key）本质上是一种**调用方身份凭证与认证机制**：它解决的是"这次 API 调用是谁发起的、是否可信"，属于**认证（Authentication）**关注点，而非"管理用户账号生命周期"的用户管理关注点。
- 「用户管理」域中的用户在本功能中仅作为**绑定的关联对象**（凭证必须归属某个用户才能创建），用户数据本身仍由用户管理域权威维护；AK/SK 的创建、启停、删除、验签全部是认证管理域的职责。
- 前端菜单入口应放在**「认证管理」菜单下**（与现有认证策略同级），而非「用户管理」菜单下；用户管理页面可提供"跳转到该用户的凭证列表"的辅助入口，但不承载凭证管理功能本身。

## Clarifications

### Session 2026-09-12

- Q: AK/SK 鉴权通过后，接口的访问权限如何判定？ → A: 完全由凭证绑定的用户的权限决定（沿用该用户的 RBAC 授权）；凭证自身不携带任何权限，既不可扩大也不缩小绑定用户的可访问范围。
- Q: 签名鉴权与现有登录态鉴权如何共存、哪些接口接受签名调用？ → A: 所有对外业务接口统一支持两种鉴权方式，登录态或 AK/SK 签名任一通过即可，权限判定走同一套逻辑。
- Q: 某 AK 连续签名验证失败时，系统是否自动封禁该凭证？ → A: 不自动封禁；连续失败仅记录结构化日志并触发监控告警，凭证状态保持"启用/禁用"二元，暴力破解防护依赖既有接口限流。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员为用户创建 AK/SK 凭证（Priority: P1）

管理员在认证管理的凭证管理页面，选择一个已有用户，为其创建一对 AK/SK 凭证。系统生成唯一的 AK（公开标识）和 SK（私密密钥）。SK 只在创建成功时**一次性明文展示**，之后任何页面都只能看到掩码形态，管理员需在创建时立即保存。

**Why this priority**: 没有凭证创建，签名鉴权链路无法开始，是一切后续能力的前置条件。

**Independent Test**: 可独立测试——创建凭证后能看到 AK 与一次性 SK、凭证出现在该用户名下的列表中；不依赖任何签名调用功能。

**Acceptance Scenarios**:

1. **Given** 系统中存在用户"张三"，**When** 管理员为其创建 AK/SK 凭证，**Then** 系统生成全局唯一 AK 与配套 SK，创建结果页一次性明文展示 SK，并明确提示"关闭后将无法再次查看"。
2. **Given** 凭证创建成功，**When** 管理员查看该用户的凭证列表，**Then** 列表中出现该凭证，SK 列仅显示掩码（不可还原为明文），其余业务字段（AK、备注、状态、过期时间、创建人、创建时间等）全量展示。
3. **Given** 管理员尝试为一个**不存在或已停用**的用户创建凭证，**When** 提交创建，**Then** 系统拒绝并返回可理解的错误提示，不产生任何凭证数据。

---

### User Story 2 - 调用方使用 AK/SK 签名调用接口（Priority: P1）

外部调用方（人或程序）持有某用户的 AK/SK，按平台约定的签名规则对请求进行签名后调用受保护接口。服务端依据 AK 找到对应凭证与用户身份，校验签名有效性、请求时效与防重放，校验通过后以该用户身份放行调用；校验失败则拒绝并返回明确的失败原因。

**Why this priority**: 这是需求的核心价值——机器对机器（M2M）调用能够安全地通过签名鉴权访问接口。

**Independent Test**: 可独立测试——用已创建的凭证签名请求受保护接口，正确签名返回成功，篡改签名/过期请求/重放请求均被拒绝；不依赖前端管理页面。

**Acceptance Scenarios**:

1. **Given** 一对处于启用状态且未过期的 AK/SK，**When** 调用方按约定签名规则发起请求，**Then** 服务端验签通过，请求以凭证绑定的用户身份被处理。
2. **Given** 调用方使用错误 SK 计算签名，**When** 发起请求，**Then** 服务端拒绝，返回"签名错误"类业务错误，不泄露任何密钥相关信息。
3. **Given** 凭证已处于禁用状态，**When** 调用方发起正确签名的请求，**Then** 服务端拒绝并返回"凭证已禁用"类业务错误。
4. **Given** 一条已被服务端受理过的签名请求被原样重放，**When** 再次到达服务端，**Then** 服务端识别为重放并拒绝。
5. **Given** 签名请求中的时间戳超出允许的时效窗口，**When** 发起请求，**Then** 服务端拒绝并返回时效相关错误，避免历史抓包长期可用。

---

### User Story 3 - 管理员查看与检索凭证列表（Priority: P2）

管理员可以查看全部凭证或按用户筛选某用户名下的凭证列表，列表分页展示，字段全量呈现（AK、所属用户、备注、状态、过期时间、最后使用时间、审计字段只读展示），并支持按 AK / 所属用户 / 状态等条件检索。

**Why this priority**: 管理可见性是运营与审计的基础，但不阻塞核心创建与验签链路。

**Independent Test**: 可独立测试——创建若干凭证后，通过筛选条件能准确过滤出目标凭证，分页与排序正确。

**Acceptance Scenarios**:

1. **Given** 系统中存在多个用户的凭证，**When** 管理员按用户筛选，**Then** 列表仅显示该用户名下的凭证。
2. **Given** 凭证数量超过单页容量，**When** 管理员翻页，**Then** 分页数据与总数正确，查询条件在翻页后保留。
3. **Given** 无任何凭证数据，**When** 管理员打开凭证列表页，**Then** 页面展示友好的空状态提示而非空白。

---

### User Story 4 - 启用 / 禁用凭证（Priority: P2）

管理员可以对任一凭证执行启用或禁用操作。禁用后该凭证的签名调用立即（或近实时）失效；重新启用后恢复可用。高危操作需二次确认。

**Why this priority**: SK 疑似泄露时的快速止血手段，是安全运营的必要能力。

**Independent Test**: 可独立测试——禁用某凭证后，该凭证的签名调用被拒绝；启用后恢复。

**Acceptance Scenarios**:

1. **Given** 一条启用中的凭证，**When** 管理员执行禁用并确认，**Then** 凭证状态变为禁用，其后续签名调用在 5 秒内开始被拒绝。
2. **Given** 一条禁用中的凭证，**When** 管理员执行启用，**Then** 凭证状态变为启用，正确签名恢复放行。
3. **Given** 管理员点击禁用，**When** 确认弹窗出现，**Then** 弹窗明确说明影响范围（该用户名下此凭证的调用将全部失败），取消则不产生任何变更。

---

### User Story 5 - 删除凭证与 SK 重置（Priority: P3）

管理员可以删除不再使用的凭证（删除前系统校验引用完整性并记录审计日志），也可以对仍在使用但 SK 已泄露的凭证执行"重置 SK"——生成新 SK 并一次性展示，旧 SK 立即失效。

**Why this priority**: 生命周期收尾与密钥轮换能力，重要但不阻塞上线。

**Independent Test**: 可独立测试——删除凭证后列表不再出现且调用被拒；重置后旧 SK 签名被拒、新 SK 签名通过。

**Acceptance Scenarios**:

1. **Given** 一条不再被使用的凭证，**When** 管理员删除并确认，**Then** 凭证从列表移除，其签名调用被拒，删除操作记录审计日志（操作人、凭证标识、操作时间）。
2. **Given** 一条仍在使用的凭证，**When** 管理员执行"重置 SK"并确认，**Then** 系统生成新 SK 一次性展示，旧 SK 立即失效（签名被拒），AK 保持不变。
3. **Given** 管理员点击删除，**When** 确认弹窗出现，**Then** 弹窗说明删除不可恢复且调用将失败，取消则不产生任何变更。

---

### Edge Cases

- 生成 AK 时若与既有 AK 冲突（概率极低），系统必须重试生成直至唯一，不允许出现重复 AK。
- 凭证绑定的用户被停用/删除时：该用户名下凭证的签名调用应被拒绝（凭证有效性依赖用户有效性）；删除用户前的引用完整性校验需将名下凭证计入引用方。
- 一个用户可拥有多条凭证（不同用途/环境各持一对），系统对单用户凭证数量设置合理上限并在超限时给出明确错误。
- 凭证设置过期时间时，过期后的签名调用一律拒绝，返回过期相关错误。
- 签名请求缺少 AK、缺少签名、缺少时间戳等不完整请求，返回参数类错误而非签名错误，便于调用方排查。
- 客户端与服务端时钟偏移在允许窗口内（如 ±5 分钟）正常放行，超出窗口拒绝并提示检查系统时间。
- 禁用/删除操作与进行中的验签并发发生时，结果必须确定（生效时刻之后到达的请求一律拒绝），不允许出现"已禁用仍放行"的持久状态。
- 所有创建、禁用、启用、删除、重置操作必须记录审计日志；重复提交需幂等处理。
- 某 AK 遭遇持续恶意签名攻击（连续失败）时：不自动封禁凭证（避免误伤正常调用方与 DoS 放大），依赖限流与监控告警发现和处置；管理员可基于告警人工禁用凭证止血。

## Requirements *(mandatory)*

### Functional Requirements

**凭证管理（认证管理域）**

- **FR-001**: 系统 MUST 支持为已有用户创建 AK/SK 凭证对，AK 全局唯一，SK 满足密码学安全强度（足够长、随机生成）。
- **FR-002**: SK MUST 仅在创建/重置成功时一次性明文展示；此后任何查询接口与页面 MUST 只返回掩码形态，且系统 MUST NOT 提供任何还原明文 SK 的途径。
- **FR-003**: 系统 MUST 在存储层面对 SK 做不可逆保护（不以明文落库），数据库泄露时不可直接还原 SK。
- **FR-004**: 每条凭证 MUST 绑定一个用户；系统 MUST 拒绝为不存在或已停用用户创建凭证。
- **FR-005**: 系统 MUST 支持为凭证设置备注与可选的过期时间；过期凭证的签名调用 MUST 被拒绝。
- **FR-006**: 系统 MUST 支持凭证的启用与禁用，禁用生效后其签名调用 MUST 在 5 秒内被拒绝。
- **FR-007**: 系统 MUST 支持删除凭证：删除前 MUST 完成引用完整性校验（作为用户删除时的引用方计入），删除 MUST 记录审计日志（操作人、凭证标识、时间）。
- **FR-008**: 系统 MUST 支持"重置 SK"：AK 不变、生成新 SK 一次性展示、旧 SK 立即失效，操作记录审计日志。
- **FR-009**: 系统 MUST 支持按 AK / 所属用户 / 状态等条件检索凭证，列表分页返回并全量展示业务字段；审计字段仅只读展示。
- **FR-010**: 单用户凭证数量 MUST 有上限约束（默认 20，超限拒绝并提示）。

**签名鉴权（调用链路）**

- **FR-010a**: 所有对外业务接口 MUST 统一支持两种鉴权方式：登录态鉴权或 AK/SK 签名鉴权，任一通过即可；两种方式最终走同一套基于用户授权（RBAC）的权限判定，禁止为签名调用另立一套授权口径。
- **FR-011**: 系统 MUST 提供基于 AK/SK 的请求签名验证能力：调用方在请求中携带 AK、签名、时间戳、随机数（nonce）等要素，服务端按约定算法校验。
- **FR-012**: 签名算法 MUST 采用业界通用的 HMAC 类签名方案（对请求方法、路径、关键头部与请求体摘要等进行规范序列化后以 SK 计算 HMAC），具体算法与签名要素在计划阶段以公开、可复现的签名规范文档形式定义。
- **FR-013**: 验签 MUST 覆盖：AK 存在且启用、凭证未过期、绑定用户有效、签名值正确、时间戳在时效窗口内（默认 ±5 分钟）、nonce 未被重放。
- **FR-014**: 验签失败 MUST 返回语义明确的业务错误（区分：AK 不存在 / 已禁用 / 已过期 / 签名错误 / 时间戳超窗 / 重放），且 MUST NOT 泄露 SK 相关信息。
- **FR-014a**: 系统 MUST NOT 因连续验签失败自动封禁凭证（凭证状态保持"启用/禁用"二元）；验签失败 MUST 记录结构化日志（含 AK、失败原因、来源标识、traceId）并接入监控告警，暴力破解防护依赖对外接口限流。
- **FR-015**: 验签通过后，请求 MUST 以凭证绑定的用户身份进入后续权限判定：**接口访问权限完全由绑定用户的授权（RBAC）决定，凭证自身不携带任何权限**，既不可扩大也不缩小绑定用户的可访问范围；签名鉴权只解决"你是谁"，不做授权豁免。
- **FR-016**: 所有涉及凭证管理的写操作（创建、启用、禁用、删除、重置）MUST 幂等或明确拒绝重复请求，并记录操作审计日志。

**前端页面**

- **FR-017**: 认证管理菜单下 MUST 新增"访问凭证"页面：凭证列表（分页、筛选、全量字段展示、状态标签）与创建入口。
- **FR-018**: 创建/重置成功后 MUST 出现一次性 SK 展示环节，含"仅展示一次"的醒目警示与复制能力。
- **FR-019**: 启用/禁用/删除/重置 MUST 有二次确认，确认内容说明影响范围；所有页面 MUST 具备加载、空、异常、无权限四态。
- **FR-020**: 后端暴露的凭证管理接口 MUST 全部被前端实际调用（契约完备），禁止长期悬空接口。

**领域与数据**

- **FR-021**: 凭证模型归类为**基础架构型模型**（治理配置数据）：允许物理删除，但删除前必须完成应用层引用完整性校验并记录审计日志；必备审计字段（创建人/修改人/创建时间/修改时间）由服务端注入，请求体禁止携带。
- **FR-022**: 凭证与用户的关联仅在业务层维护（无数据库外键），关联字段建立索引。

### Key Entities *(include if feature involves data)*

- **访问凭证（AccessCredential）**：一次 AK/SK 签名凭证。关键属性：AK（全局唯一公开标识）、SK（仅创建时明文可见，存储为不可逆形式）、所属用户、备注、状态（启用/禁用）、过期时间（可选）、最后使用时间、审计字段（创建人/修改人/创建时间/修改时间，服务端注入）。
- **用户（User）**：既有 IAM 用户管理域实体，本功能中仅作为凭证的绑定目标；一个用户可绑定多条凭证。
- **签名验证记录要素**：AK、签名值、时间戳、nonce——调用方每次请求携带，服务端校验并做 nonce 防重放（短暂时效窗口内去重），不作为持久业务实体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可在 1 分钟内完成为指定用户创建 AK/SK 凭证并保存 SK 的全流程。
- **SC-002**: 使用有效凭证的正确签名请求验签通过率 100%；错误签名、过期、重放、禁用凭证的请求 100% 被拒绝（安全验收零漏放）。
- **SC-003**: 禁用或删除凭证后，对应签名调用在 5 秒内开始被拒绝。
- **SC-004**: 任何已创建凭证的查询结果中均无法获得 SK 明文（掩码展示），数据库层无法还原 SK。
- **SC-005**: 100% 的凭证管理写操作留下审计日志（操作人、对象、动作、时间）。
- **SC-006**: 验签处理不显著增加接口耗时（相比无签名调用，新增开销为毫秒级），不影响正常调用方体验。

## Assumptions

- 本功能归属 **IAM 认证管理域**（见文首裁决）；用户管理页面仅提供"查看该用户凭证"的辅助跳转入口。
- 签名方案采用业界通用的 HMAC 类签名（类 AWS SigV4 / 阿里云 RPC 签名风格），具体算法、参与签名的要素与请求头约定在 `/speckit-plan` 阶段确定并产出签名规范文档，供调用方实现 SDK。
- 防重放采用"时效窗口 + nonce 去重"组合，nonce 去重窗口与时间戳窗口一致（默认 5 分钟），去重存储可容忍实例重启后的极小概率误放行。
- 默认允许单用户最多 20 条凭证、时间戳窗口 ±5 分钟；以上默认值可在配置中调整，不构成需求歧义。
- 签名鉴权面向 xxx-service 对外 HTTP 接口；内部服务间调用的认证机制不在本期范围内。
- SK 明文仅在创建/重置响应中返回一次属于业界标准做法（如云厂商 AK/SK），由此产生的"丢失后需重置"为可接受权衡。
