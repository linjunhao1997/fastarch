## 1. 模型与字段

| 项 | 落地 |
| --- | --- |
| 归属人 | `t_task.owner_id`（account_id），任务归创建人所有 |
| 归属角色 | `t_task.role_id`，创建时所用角色，不再改派 |
| 父任务 | `t_task.parent_task_id`，0=顶层，非 0=基于上游父任务派生 |
| 契约 | `Task.parent_task_id/parent_task_title/owner_id/owner_name/child_total/child_done/child_open` |
| 视图 | `mine`（本人+当前角色）/`upstream`（上游角色，只读）/`created`/`all`（boss+pjm） |


子任务 #24 完成后，#23 再完成：成功。门槛只看**直接下级**的 `status=open`；下级已完成或已作废不阻塞。由于每一级都受同一门槛约束，整棵树实际是逐级向上完成。

## 4.1 父任务有问题时禁止派生（实测）

在父任务 #31 上向需求分析师抛一条未闭环问题 q12，再以需求分析师身份基于 #31 建子任务：

```text
业务码 3001033：父任务还有未闭环问题，不能基于它新建子任务；先等父任务的问题闭环
```

问题闭环后，父任务恢复可派生。页面上父任务处于 blocked 时，“基于此建我的任务”按钮不显示，改为提示“父任务有问题待闭环”。

## 7. 残余风险

- 单账号：所有任务 `owner_id` 相同，无法真实覆盖跨账号越权；逻辑已按 account_id 校验。
- 问题仍按“目标角色”路由，不按人；一个角色多人时，问题仍可能被同角色其他人回答。
- `upstream` 返回所有上游角色的任务（含已完成），用于建子任务；尚未按“直接父角色”收窄。
- 历史任务已回填归属人，但父子关系未自动重建；本次用 #25–#29 新建了完整链。
- 前端只做构建级验收，未做浏览器人工点选。
