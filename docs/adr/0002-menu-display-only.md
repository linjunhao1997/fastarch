# 菜单回归纯展示配置，授权仅角色直授码

菜单不再参与授权。权限快照只取角色直授权码（`t_r_role_permission`）；`t_menu.permission_code` 语义从"绑菜单即授此码"翻转为"展示此菜单所需的码"，纯前端展示门槛，不授予任何权限。角色-菜单绑定（`t_r_role_menu`）保留，仅决定菜单可见性。

## 为什么

ADR 0001 把菜单/字典抽为每服务自持。叠加 2026-11-15"勾菜单=授码"裁决后，菜单绑定成了一个**两域共管的事实**：展示结构归宿主，授权效果归 IAM。第二个宿主（order）接入时，IAM 的快照回源只读自己的库，看不见宿主本地的菜单绑定——菜单授权推导跨宿主即断。

字典只有展示身份，自持干干净净；菜单被"勾菜单=授码"赋予了授权身份，才被撕成两半。病根不在"菜单自持"，而在两条裁决同时成立必然产生的跨服务过桥费。

## 决策（2026-11-17 用户确认，裁决 B）

- **废除菜单授权推导**：权限快照 = 角色直授启用码，菜单不产码。登录与回源均不再加载角色绑定菜单。
- **`t_menu.permission_code` 语义翻转**：展示所需码（可空）。前端按用户持有码二次过滤菜单显隐；服务端不因此授予权限。
- **菜单可见性两层**：服务端 `my-menu-tree` 按角色绑定过滤（基础层，不变）+ 前端按 `permission_code` 与持有码过滤（额外层）。
- **API 访问仍服务端 fail-closed 判码**：前端隐藏菜单只是 UX，不是安全边界。
- 角色删除级联清理 `t_r_role_menu` 保留（可见性完整性）。

## Considered Options

- **A. 两条裁决都保留 + 投影上报**：宿主勾菜单后把派生码上报 IAM 集中登记（1 表 + 1 RPC + 1 钩子）。保留"勾菜单即授权"便利，但为一条便利规则养一个跨服务同步机制。否决：复杂度税超过便利价值。
- **C. 绑定写 IAM（结构/字典仍自持）**：域归属最纯（授权行为归授权中心写），但侧边栏读绑定引入 IAM 运行时依赖（ADR 0001 想避免的），且 contrib 绑定存储须抽象成钩子，重构面更大。否决。
- **B（选定）. 菜单纯展示，码全部 IAM 角色页手动授**：域分离最干净，同步机制整个消失。代价：管理员授页面查看码多一步操作；须保持菜单绑定与码授予一致，避免"看得到页面却 403"。

## Consequences

- 快照 loader / 登录去掉菜单加载，查询更少；contrib `menu.Config` 移除 `OnRoleMenusChanged` 钩子（无宿主需要绑定变更失效快照）。
- order-service 接入大幅简化：不再需要投影表 / `SyncRoleMenuCodes` / `OnMenuChanged` 钩子；内部契约 `FederationService` 只需 `GetAccountRoleIds`/`RoleExists`（侧边栏角色钩子）。
- 前端 `buildMenuItemsFromTree` 按持有码过滤；菜单管理页字段改称"展示所需权限码"。
- 种子/演示：非 admin 用户现在需显式授予页面查看码才看得到菜单（推导不再自动授）；admin 旁路不受影响。
- 推翻 2026-11-15 菜单授权推导裁决。
