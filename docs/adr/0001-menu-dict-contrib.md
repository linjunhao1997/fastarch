# 菜单/字典抽为 contrib 通用能力，每服务嵌入自持

菜单（t_menu + t_r_role_menu）与字典（t_dict_type/t_dict_item）的实现从 iam-service 抽到 `contrib`（model + pkg/menu + pkg/dict + pkg/bizerr），契约仍共享 `iam.v1.MenuService/DictService`。每个应用服务嵌入 contrib 即获得自己的菜单/字典能力，数据在自己库里；IAM 当前是宿主之一，不再是"替所有应用管菜单/字典"的平台方。

## 为什么

- 菜单/字典是每个应用都需要的通用配置能力，不是 IAM 授权域的本体（IAM = 认证 + 授权关系）。
- 业务服务运行时读自己的枚举/导航不应依赖授权中心的可用性。
- 统一到一个平台服务管所有应用的数据，压力集中且语义错位；"每个应用自己维护"更贴合多应用裁决的数据隔离原则。

## 设计

- **宿主差异经 Config 钩子注入**（fail-closed，必填钩子缺失即构建失败）：应用上下文、账号/管理员身份、角色存在性与绑定、权限码校验（授权词汇规则归宿主）、快照失效回调。
- **iam 宿主语义不变**：菜单授权推导（勾菜单=授码）、服务段隔离校验、按应用数据隔离、业务错误码全部保持，前端与迁移 SQL 零改动。
- **分页/模糊过滤等纯逻辑随 contrib 包自带**，不依赖宿主 helper。

## Considered Options

- 独立平台配置服务：为两张表起一个服务，运行时耦合依旧（只是换了依赖对象），否决。
- 菜单/字典彻底出 IAM 域、各前端硬编码导航：失去管理员维护展示结构的能力，用户明确不要，否决。
- 留在 iam-service 原地：域错位持续，order 等应用接入时无处安放自己的菜单/字典，否决。

## Consequences

- order 等新服务接入菜单/字典：引用 contrib，注入自己的钩子，建自己的表（迁移 SQL 自持）；运行时读自己的库。
- 统一控制台管理各应用菜单/字典的"联邦路由"（网关按应用转发到对应服务）推迟到第二个宿主出现时设计。
- contrib 与宿主间的权限码校验、快照失效等耦合点全部收敛在 Config 钩子上，新增宿主只需实现钩子。
